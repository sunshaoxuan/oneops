# プロジェクト強制規約

更新日: 2026-08-05

## Git リポジトリとリリースブランチ

OneOps の正式なリモートは `origin` のみとし、URL は `https://github.com/sunshaoxuan/oneops.git` とします。正式なリリースブランチは `master` です。すべてのテスト済み変更は `origin/master` へ直接コミットしてプッシュします。

ユーザーが現在のタスクで明示的に指示した場合を除き、別のローカルブランチ、リモートブランチ、Pull Request を作成しません。変更前に `origin/master` を取得して確認し、プッシュ後にローカル `HEAD` と `origin/master` の一致を確認します。

## 文書、コメント、バージョン

プロジェクトが作成・管理する文書、要件、調査記録、運用説明、コードコメント、スクリプトコメントは日本語で記述します。中国語と英語は、画面の多言語表示文言、外部データ、テストフィクスチャ、API の固定値、第三者ライセンス原文に限って使用できます。

機能、データモデル、インターフェース、運用方法、プロジェクト規約を変更した場合は、関連する要件、説明、調査証跡も同時に更新します。

ルートの `VERSION` にプロジェクトの現行バージョンを保存します。正式リリースでは `CHANGELOG.md`、アプリケーションの `package.json`、Portal の画面表示バージョンを同期し、`v<version>` の Git タグを作成します。詳細は `D:\nginx\docs\VERSIONING.md` を参照してください。

## 設計と実装の強制原則

以下の原則は、新規開発と変更対象の設計・実装を拘束します。廃止対象の互換処理、移行処理、フォールバックは、対象機能を現行契約へ統一する変更と同時に削除します。

1. 後方互換性を保持しません。廃止対象は直接削除し、互換レイヤー、移行処理、フォールバックを追加しません。
2. 現行要求を満たす最も単純な実装を選択します。予防的な抽象化、不要な設定層、将来用途だけの拡張点を追加しません。
3. システムは段階的に構築します。最初に最小のエンドツーエンド実装を動作させ、その上に必要な機能を追加します。未完成の複雑性を理由に、動作中の基盤を分解しません。
4. コンポーネントをモジュール化し、関心事を分離します。
5. 成熟し継続的に保守されるライブラリを優先します。明確な理由がない限り、既存ライブラリの機能を独自実装で置き換えません。
6. 新しいパッケージや独自実装を検討する前に、プロジェクトの既存依存関係で利用できる機能を確認します。
7. アーキテクチャの意思決定は長期運用を前提に行います。「先にこうして後で置き換える」という暫定案を採用しません。
8. 同じ問題を解決した成熟製品を調査し、実証済みのパターンを採用します。ゼロから独自方式を発明しません。

## 台帳の主キーと参照

すべての台帳と業務レコードは、一般画面には表示しない独立した安定物理 ID を持つ必要があります。

業務コードは、ユーザーによる識別、検索、業務上の一意制約に使用します。業務名称とその他の項目は業務情報の表現に使用します。台帳間の強参照では、参照先台帳の物理 ID を保存し、データベース外部キー制約で参照整合性を保証します。

変更可能な業務コードや名称を、台帳と業務レコード間の強参照外部キーとして使用しません。この規約は既存および今後追加するすべての台帳と業務レコードに適用します。

組織機関の区分はシステム台帳です。組織機関は `classification_id` 物理外部キーで区分台帳を参照し、区分名称を自由入力文字列として組織機関テーブルへ保存しません。

## プロジェクトルート

`D:\nginx` を本システムのプロジェクトルートとします。ソースコード、設定、ランタイム、依存関係、ログ、起動エントリーポイントは、このディレクトリから解決できる必要があります。

OneOps は EnvPortal に配備済みの Windows ドメイン認証結果を再利用します。EnvPortal ユーザーは、一度だけ実行する監査可能な移行で OneOps へ登録できます。旧ロールは OneOps 標準ロールへ変換し、移行後にランタイム依存関係を残しません。その他の EnvPortal 業務データは、それぞれ独立した一回限りのインポート処理で移行します。

Windows SSO の画面入口は、EnvPortal SSO URL とプロファイル検証 URL の両方が設定済みの場合だけ有効化します。自動ログイン設定だけを根拠に SSO 入口を表示してはいけません。

## ユーザー、アイデンティティ、権限

OneOps は、ユーザー、外部アイデンティティ、セッション、ロール、権限、ロール権限、ユーザーロール割当、監査記録を独立して管理します。ドメイン認証プロキシは署名済みのドメインアイデンティティアサーションだけを送信し、ユーザー台帳と権限を管理しません。

認証と認可に関するレコードも物理 ID 規約に従います。バックエンド API を権限判定の最終境界とします。パスワード、セッショントークン、CSRF Token、SSO チケット、共有秘密をログや監査詳細へ記録しません。

詳細要件は `D:\nginx\docs\AUTHENTICATION_AND_RBAC_REQUIREMENTS.md` を参照してください。

システム管理の情報設計では、基本台帳とアイデンティティアクセス管理を分離します。組織区分、製品、版数は基本台帳へ配置し、ユーザー、ロール権限、認証監査は独立したユーザー管理グループへ配置します。各機能には細分化した第 2 階層メニューから遷移します。

ロール権限の編集画面は、機能ノードを行、操作種別を列とする権限マトリクスで表示します。画面には選択中の言語だけを表示し、各交点の位置を固定して整列させます。権限 Code は補助説明で確認できるようにし、権限が存在しない交点を明示します。操作種別は、情報を確認する「閲覧」、データや設定を変更する「管理」、問合検索や AI 支援などの業務処理を起動する「実行」として利用者向けに説明します。

システム管理の第 2 階層ナビゲーションはページ内容の上部に配置します。基本台帳とユーザー管理は横方向のサブメニューを使用し、個別機能はドロップダウン項目として表示します。システム管理の内容領域には固定の左側第 2 階層ナビゲーションを使用しません。

製品版数一覧は数値セグメントによる自然昇順を使用します。版数の並び順に文字列辞書順を使用せず、`2.9.2` を `2.11.1` より前に配置します。

システム管理の第 1 階層メニューとページ大見出しには同じ名称を使用し、「管理」などの省略された入口名称を使用しません。

ログイン済みユーザーは、右上のアカウントメニューからプロフィールを開き、自分の表示名を変更できます。プロフィールのユーザー名とメールアドレスは読み取り専用です。ユーザーが手動保存した表示名を、その後の Windows SSO ディレクトリ同期より優先し、プロフィール更新監査を記録します。

左側ブランド領域の OneHR ロゴ、製品名、多言語サブタイトルは安定した配置を維持します。サブタイトルはデスクトップサイドバーとモバイルドロワーの両方で 1 行表示とし、幅不足による改行を発生させません。

左側の第 1 階層ナビゲーションは、「ワークベンチ」「タスク」「顧客情報」「問合支援」「製品構築」「AI助手」「ナレッジ」「コードインサイト」「レポート」「基本台帳」「システム管理」の順序で表示します。「ツールセンター」は第 1 階層ナビゲーションおよびワークベンチの遷移入口に配置しません。個人タスクは `personal.tasks.use` 権限、AI助手は `ai.assistant.use` 権限を持つユーザーに表示します。個人タスクは `/tasks`、顧客情報は `/customers`、AI助手は `/ai-assistant` を使用します。旧 `/environments` は `/customers` へ正規化します。各機能の状態とデータを混在させません。

第 1 階層画面、基本台帳の各機能、システム管理の各機能には安定した同一オリジン URL を割り当てます。画面遷移はブラウザー履歴へ追加し、再読み込み時は URL から同じ機能を復元します。ブラウザーの戻る操作と進む操作では `popstate` を処理し、履歴が示す機能へ遷移します。権限のない機能または未知の URL は、利用可能な最初の機能へ正規化します。

ワークベンチのメインコピーには、節度があり、正確で、ブランド品質を備えた表現を使用します。日本語は「運用のいまを見渡し、次の一手を確かに。」に統一し、中国語と英語も同じ意味と語調を保ちます。

製品構築は OneOps 内部機能として動作させます。ブラウザーは OneOps の HTTPS エントリーポイントを使用し、旧コンソールは 8091 を待ち受けません。構築画面の機関名称は、共通コンテキストで選択中の組織機関名称を初期値として設定し、入力欄は編集可能にします。履歴タスクにはタスク保存時の名称を表示します。

製品構築は OneOps 内でネイティブなワークスペーススタイルを使用します。単独ページ用の製品ナビゲーションと言語選択は埋め込み画面に表示しません。内容は利用可能領域全体を使用し、二重スクロールを発生させません。OneOps 内部 Gateway は `127.0.0.1:8092` を固定使用します。構築 Worker のパイプ異常は Gateway 内で隔離して復旧し、SSO に影響を与えません。

顧客台帳機能のメニューとページタイトルには完全な名称を使用します。日本語は「顧客情報」、中国語は「客户信息」、英語は「Customer information」に統一します。顧客情報は基本情報、契約情報、サービス情報、ネットワーク環境、問合情報、関連タスク及びチケットで構成し、従来の環境台帳はネットワーク環境のサーバー詳細情報で維持します。

共通コンテキストの組織機関選択は、機関コードと機関名称の両方で部分一致検索できる必要があります。照合時は大文字小文字と全角半角を正規化し、選択後は機関名称を表示します。

OneOps は OHR0067 の既存 EnvPortal ドメイン認証プロキシから短期アイデンティティトークンを取得します。OneOps サーバーは EnvPortal にトークンを検証し、ユーザープロフィールを読み取った後、OneOps 自身のデータベースに外部アイデンティティ、セッション、既定の `VIEWER` ロールを作成します。ランタイムでは EnvPortal ロールを信頼または受け渡しません。一回限りのユーザー移行では、認証と RBAC 要件の固定マッピングに従って OneOps 標準ロールを作成します。移行後の認可は OneOps データベースだけを参照します。

本プロジェクトはリアルタイム開発、リアルタイム試験、リアルタイム配信及びリアルタイム公開を原則とします。ソースコード、設定、データベースマイグレーション、スクリプト、要件文書を変更した場合、ローカル継続的デリバリータスクは全テスト、本番ビルド、リリース検証、Commit、`origin/master` への Push 及び正式公開を直ちに実行します。テスト失敗時は現在のリリース版を維持します。継続的デリバリーの高権限タスクが監視するディレクトリは、一般ユーザーの書込みを制限します。

フロントエンド、API クライアント、関連要件文書だけを静的配信する場合は OneOps Gateway を再起動しません。Gateway、構築機能、データベース、ランタイムスクリプトを変更した場合はローリング配信を使用します。新成果物を予備の `127.0.0.1:8094` と内部互換 Gateway `127.0.0.1:8095` で起動し、Health 合格後に Nginx を平滑 Reload して流量を切り替えます。主系 `127.0.0.1:8092` と内部互換 Gateway `127.0.0.1:8093` の新成果物が Health 合格した後に流量を主系へ戻し、予備系を終了します。Portal Asset は先に配置し、`index.html` を原子的に交換します。

## 常時稼働

OneOps の常時稼働は Windows タスク `OneOps Runtime Supervisor` が担当します。システム起動時と運用ユーザーのログオン時に開始し、Docker Desktop、保護済み PostgreSQL ボリューム、データベース、Gateway、自動 SSO、Nginx HTTPS を 30 秒間隔で確認します。

復旧処理は外部ボリューム `onehr-operations-postgres-data` の存在を必須条件とします。外部ボリュームが存在しない場合は空の代替ボリュームを作成せず、異常を記録して停止します。詳細なインストール、状態確認、復旧、ロールバックは `D:\nginx\docs\RUNTIME_AVAILABILITY.md` に記録します。

## Spring Boot バックエンド置換

OneOps 0.8.0 のバックエンドは、単一の Spring Boot 実行プロセスとして構築します。業務機能は Spring Modulith のモジュールで分離し、モジュール間通信に HTTP、追加待受ポート、サービスレジストリを使用しません。

Nginx HTTPS を唯一の公開入口とし、Spring Boot の正式主系は <code>127.0.0.1:8092</code> を待ち受けます。ローリング配信中だけ予備系 <code>127.0.0.1:8094</code> を併用します。フロントエンド、公開 API、Cookie、CSRF、SSE、PostgreSQL の既存業務表、暗号化資格情報、Python Worker の標準入出力契約を維持します。

業務更新の Transaction 境界は Spring Application Service に置き、全業務モジュールで一つの DataSource と Transaction Manager を共有します。外部 HTTP、SSE 待機、Python Worker 待機を DB Transaction 内で実行しません。

実装の正本は <code>D:\nginx\docs\SPRING_BOOT_BACKEND_DETAILED_DESIGN.md</code> とします。本番環境の Backend 実行主体は一つに限定し、全受入条件の合格後に固定ポート 8092 を Spring Boot へ一括切替します。

2026年8月3日の実装開始時点では、認証、基本台帳、環境情報、環境端点資格情報を Spring Boot 側へ実装しました。未移行 API は Spring が管理する本機専用互換ブリッジへ転送し、外部入口と Nginx の構成を維持します。互換ブリッジを正式運用へ残す条件は、D04 から D11 の契約、権限、性能、Browser 検証が完了していない期間に限ります。
