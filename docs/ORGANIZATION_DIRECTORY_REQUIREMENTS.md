# 组织机构档案需求

更新时间：2026-07-23

## 画面

1. 台账标题不得显示 PostgreSQL 等后台产品名。
2. 字段标题和校验文案必须遵循 i18n。日文使用「区分」「機関コード」「機関名」「略称」「保守有無」，中文使用「区分」「机关代码」「机关名」「略称」「保守有无」。
3. 操作列固定在表格右侧，在不同画面宽度下保持完整可见。
4. 单项操作使用带无障碍名称和悬浮提示的图标。当前仅提供编辑图标。作废、删除等操作在业务规则确认后增补。
5. 物理 ID 不显示在普通画面。
6. 业务字段列允许拖动表头分隔线调整宽度，并将列宽保存到浏览器。机关名和略称吸收画面剩余宽度。
7. 点击区分、机关代码、机关名、略称和保守有无的表头，可依次按升序和降序排序。拖动列宽手柄时不得触发排序。
8. 操作列按图标数量计算固定宽度。当前一个图标对应 56 像素。
9. 每页行数支持 20、50、100，默认 20。用户选择即时生效并保存，容量变化时回到第一页。
10. 正文允许自动换行，完整字符不得因固定省略号而丢失。
11. 组织机构台账标题栏不显示数据库运行状态。数据库健康度属于系统监控信息，不属于组织机构档案的业务状态。
12. 组织机构维护画面管理全部组织机构，不显示“共通上下文”的单一机关选择器，也不按当前上下文机关过滤台账。
13. 表头和正文使用易读的大字号与舒展行高。机关 Code 使用无边框、无底色的纯文本样式，并通过等宽字体和数字间距保持清晰。
14. 用户首次进入组织机构台账时，默认按机关 Code 升序排列。用户修改排序字段或升降序后，系统将排序选择保存到浏览器，并在刷新或再次进入画面时恢复。
15. 保守有无是受控枚举，画面只能选择 `〇`、`✕` 或空值，不允许自由输入。后台和数据库必须执行相同约束。数据源中的“有”“无”等写法在导入时归一化为对应符号。无法仅用枚举表达的例外说明必须保留到组织机构备注中。
16. 备注允许维护最多 1000 个字符，用于保存保守条件、来源例外和其他补充说明。文化庁的“文部科学本省と一緒”归一化为保守 `〇`，原文保存到备注。
17. 从组织机构长列表切换到其他主功能时，页面必须自动回到顶部，不得继承长列表的纵向或横向滚动位置。内容较少的占位功能页应使用紧凑布局，在常见桌面视口内不产生多余滚动条。

## 数据模型

区分是独立的系统档案，组织机构中不得使用自由文本字段。区分档案包含物理 ID、唯一业务代码和名称。普通画面显示区分名称，组织机构编辑画面从区分档案中选择。

区分档案统一在“管理”中的“基本档案管理”维护，当前提供查询、新增和编辑功能。

组织机构档案包含物理 ID、区分物理 ID、业务代码、机关名、略称、保守有无、问合系统客户 Code 和备注。物理 ID 是数据库主键，业务代码保持唯一约束。`organizations.classification_id` 必须引用区分档案的物理 ID，并由数据库外键约束保证引用完整性。

## 外部システム対応

問合システム顧客 Code は組織機関台帳の編集画面で管理する。一般業務画面には編集操作を配置しない。

対応値は `customer_information_settings` に保存し、組織機関物理 ID で `organizations.id` を参照する。設定レコード自身も独立した UUID 物理 ID を持つ。

問合システム顧客 Code は機関 Code と同じ場合も、外部サイトとの照合が完了した対応レコードとして保存する。未照合の既存機関は問合検索時に機関 Code を有効値として使用できる。

組織機関台帳の問合システム顧客 Code 列は保存済みの対応値だけを表示する。問合検索時の機関 Code 代替値を台帳列へ表示せず、同期済み、競合及び未一致を画面上で区別できるようにする。

自動同期した対応レコードは、問合ソース設定の物理 ID、外部顧客内部 ID、外部顧客名及び最終同期日時を保持する。外部顧客内部 ID を一意に解決できない場合も、Code と名称が一意に一致する対応は保存し、内部 ID だけを空欄とする。

追加及び変更には `organizations.write` を必須とし、組織機関更新として操作監査へ記録する。

其他业务档案需要强关联组织机构或区分档案时，也必须使用被引用档案的物理 ID 作为外键。

当前数据源只提供区分名称，没有区分 Code。系统暂时按名称生成稳定且唯一的 `CLASS-` 业务代码。后续数据源提供正式区分 Code 时，应保留区分物理 ID 并校正业务代码，使现有组织机构外键无需变更。

## 数据源与同步

系统配置文件 `app/config/system.config.json` 保存组织机构数据源清单，允许登记多个数据源。

問合サイトの顧客台帳は `onehr-upds-customer-directory` として同じデータソース一覧に登録する。接続資格情報は設定ファイルへ保存せず、システム管理の `ONEHR_UPDS` 設定を物理 ID で参照する。自動同期間隔は 1 日とする。

数据源 1：

`D:\nginx\refs\★各機関情報一覧*20250530*サポート確認.xlsx`

原始来源为 `\\192.168.21.248\common\TS課\03.導入機関一覧\参考資料`，运行时使用放入工程 `refs` 目录的受控副本。

从工作表 `機関別導入製品一覧 (サポート確認後)` 统计并导入区分、机关 Code、机关名、略称和保守有无。导入器在前 50 行内识别本地化表头。数据源出现新的区分名称时，先补充区分档案，再把区分档案的物理 ID 写入组织机构外键。

同步策略固定为：

1. 补充缺失档案。
2. 只补充现有档案的空字段，不覆盖已有业务信息。
3. 不因外部数据缺失而删除现有档案。
4. 同一业务代码出现不同名称时保留现有记录。

现有档案使用 `LEGACY-` 临时代码且机关名与数据源完全一致时，保留物理 ID，将业务代码校正为数据源正式机关 Code，并补充空字段。已有正式业务代码不执行该校正。

問合サイト同期は機関 Code で検索し、機関名又は略称と外部顧客名が正規化後に一意に一致したレコードだけを追加又は補足する。同 Code 異名、既存対応値との不一致及び複数名称一致は上書きせず、システムメッセージ用 TODO ログへ残す。外部サイトに存在しないことを理由に、既存の組織機関及び対応レコードを削除しない。

## 2026-08-05 問合サイト同期結果

1. 問合サイトから顧客選択肢 260 件を取得した。
2. 組織機関 106 件を機関 Code で照合した。
3. Code と名称又は略称が一意に一致した 84 件を対応台帳へ保存した。
4. 84 件すべてに対応レコード UUID、組織機関物理 ID 外部キー、問合ソース設定物理 ID 外部キー、外部顧客名及び同期日時を保存した。
5. 外部顧客内部 ID は 71 件で一意に解決した。残り 13 件は業務 Code と名称の対応を保存し、内部 ID を空欄とした。
6. 同 Code 異名 19 件は既存台帳を変更せず、システムメッセージ実装用 TODO とした。
7. Code 検索結果なし 3 件は未対応のまま保持した。

当前数据质量记录：

1. 数据源共有 105 行有效记录和 103 个唯一机关 Code。
2. Code `0001` 同时对应「文部科学本省」和「文部科学省共済組合」，按同 Code 异名冲突处理。
3. Code `9141` 出现两次且名称相同，按重复记录合并。
