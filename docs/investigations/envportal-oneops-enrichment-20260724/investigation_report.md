# EnvPortal 数据的 OneOps 结构增强调查

## 调查目标

确认初始导入是否充分利用 OneOps 的环境分组、制品版数、功能模块和连接端点机制，并修正扁平迁移。

## 结论

1. 初始批次把 EnvPortal 的 `構築環境名` 直接作为环境名称，统一放入“基本環境”，用途统一为“其他”。
2. 初始批次没有建立制品版数关系，也没有把 URL、DB 和 RDP 拆分为环境端点。
3. OneOps 已有共通制品“U-PDS人事給与”，其正式版数为 V6 和 V7。
4. 机构别制品资料显示四个目标机构均有 V6 候选，并包含机构级制品与模块候选。
5. 机构级 V6 不能单独证明具体环境的正式版数。结合 EnvPortal 的 UHR 环境标识后，可以形成环境级待确认关系。
6. 机构级制品列不能直接生成正式功能模块。系统只对正式模块档案进行精确匹配，未匹配项目保留为候选。
7. URL、DB 类型、DB 版数、非秘密 DB 连接信息和已匹配 RDP 可以确定地转换为 OneOps 环境端点。

## 实施结果

1. 新增 OneOps 结构增强导入档案版本 2。
2. 批次 2 增强既有 4 个环境，没有创建重复环境。
3. 四个环境进入“お客様環境”分组，物理 ID 保持 4、5、6、7。
4. 共建立 9 个环境端点。
5. 共建立 4 个 U-PDS人事給与 V6 待确认关系。
6. 正式模块档案为空，本批次建立 0 个模块关系。
7. 四个机构的制品资料行以 `PRODUCT_CANDIDATE` 保存在脱敏暂存区。
8. 重复执行识别为同一批次，数据库数量和环境修订号保持不变。

## 风险与边界

1. 四个环境的生产或检证用途仍缺少可靠来源，保持“其他”。
2. V6 关系需要人工确认后转为已确认。
3. 功能模块需要先建立正式主档，再按候选资料审核关联。
4. 两条社内 RDP 和五条遗留标签记录继续等待归属确认。
5. VPN 数据仍需后续资料分析、安全存储和审核流程。
