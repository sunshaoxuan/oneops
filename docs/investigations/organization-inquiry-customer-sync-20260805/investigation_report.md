# 問合サイト顧客対応同期 調査及び実装記録

更新日: 2026-08-05

## 目的

利用者が問合サイトの顧客対応を一件ずつ調査せずに済むように、登録済み UPDS 接続を使って組織機関台帳を一括照合し、安全に特定できる対応を自動補足する。

## 実サイト確認

1. 問合検索画面の顧客選択肢は 260 件である。
2. 顧客選択肢は站点内部の数値 ID と顧客名を保持し、業務 Code は選択肢へ含まれない。
3. 検索条件 `cuc` へ機関 Code を送信すると、対象 Code の問合結果を取得できる。
4. 同じ Code に複数の顧客名が存在する場合がある。Code だけでは自動確定せず、機関名又は略称との一意一致を必要とする。

## 同期規則

1. 全組織機関を機関 Code で順次検索する。
2. NFKC、空白除去及び小文字化後の機関名又は略称と外部顧客名を比較する。
3. 名称が一意に一致した場合だけ対応レコードを保存する。
4. 外部顧客内部 ID を一意に解決できる場合は同時に保存する。解決できない場合は Code、外部顧客名及びソース物理 IDを保存する。
5. 既存の異なる対応値、同 Code 異名及び複数名称一致は競合とする。
6. 外部に存在しない組織機関及び対応を削除しない。
7. 競合は `SYSTEM_MESSAGE` 実装用 TODO ログへ残す。

## 実行結果

| 項目 | 件数 |
| --- | ---: |
| 組織機関 | 106 |
| 外部顧客選択肢 | 260 |
| 保存した対応 | 84 |
| 外部顧客内部 ID 解決済み | 71 |
| 外部顧客内部 ID 未解決 | 13 |
| 同 Code 異名 | 19 |
| Code 検索結果なし | 3 |

データベース反向確認では、対応 84 件すべてに UUID、組織機関外部キー、問合ソース設定外部キー、顧客名及び同期日時が存在し、無効な強参照は 0 件だった。組織機関総数は同期前後とも 106 件である。

## Browser 受入による返工

最初の正式画面確認で、組織機関台帳の問合システム顧客 Code 列が空欄だった。正式流量は Spring Backend の `MasterDataService` が組織機関 API を提供しており、Node Gateway だけに追加した対応読取及び保存が Spring 側に存在しなかったことが原因である。

Spring Backend の一覧 SQL へ対応台帳結合を追加し、組織機関作成及び更新でも対応レコードを物理 ID で保存するように修正した。同じ Code を再保存した場合は同期元、外部顧客 ID、名称及び同期日時を保持し、Code が変更された場合だけ同期由来情報を解除する。実 PostgreSQL の作成、読取、更新及び自動 Rollback 試験を追加した。

継続配信監視が Java 及び XML を対象外としていたため、監視対象へ追加した。これにより Spring Backend の変更も Gateway 再起動を伴う正式配信対象となる。
