# Backlog 検索テンプレート及び顧客課題集約 調査及び実装記録

## 1. 当初目的

顧客画面の Backlog 課題を、顧客単位で複数プロジェクトから取得する。プロジェクトごとに異なる顧客自動属性を使用し、同一画面で有効な検索テンプレートを同時に実行する。取得結果は同じ表示項目へ正規化し、Backlog 課題 ID で重複を除いて表示する。

## 2. 確認結果

| 確認事項 | 確認結果 | 根拠 |
| --- | --- | --- |
| TS2_ITS | プロジェクト ID `155893`、自動属性「機関名」、type ID 5、項目 112 件 | Backlog API 実取得 |
| TECH_SUPPORT | プロジェクト ID `155379`、自動属性「顧客」、type ID 6、項目 107 件 | Backlog API 実取得 |
| OHR_TOKYO | 顧客用自動属性なし。件名照合テンプレートの対象にできる | Backlog API 実取得 |
| 課題絞り込み | リスト型は `customField_{id}[]`、テキスト型は `customField_{id}` を使用する | Backlog Developer API 及び実 API 検証 |
| 顧客値照合 | Code、名称、略称及び `【Code】名称` を候補として自動属性項目へ照合する | `external-task-settings.mjs` |
| 課題集約 | テンプレートを順番に実行し、共通課題モデルへ変換後、課題 ID をキーに重複排除する | `BacklogSystemSourceClient.listIssuesByTemplates` |
| 表示項目 | テンプレート固有の出力項目を持たず、既存の Backlog 課題表示モデルへ統一する | `normalizeIssue`、API Client 型定義 |

## 3. 実装内容

1. `backlog_search_templates` を追加し、Backlog 課題検索テンプレートをシステム共通で管理する。
2. テンプレートはプロジェクト、フィルター項目、顧客値照合元、表示順及び有効状態を保持する。
3. システム管理画面でプロジェクトを選択すると、そのプロジェクトの Backlog 自動属性一覧を取得する。
4. 自動属性一覧へ「件名」を追加し、自動属性を持たないプロジェクトでは件名内の顧客値照合を選択できる。
5. 複数テンプレートの有効スイッチを同じ画面で操作できる。
6. リスト型及びテキスト型の顧客照合を実装する。数値、日付、ユーザー及びバージョン型は顧客照合対象から除外する。
7. 複数テンプレートの課題を全件取得し、同一 Backlog 課題 ID を一件へ統合する。
8. 統合後に更新日時順で並べ、ページングを適用する。
9. 顧客画面の旧顧客別プロジェクト対応 UI を停止し、システム共通テンプレートの表示へ切り替える。既存テーブル及び旧 API は互換用に保持する。

## 4. 実行時検証

保存済み API Key は `/api/v2/users/myself` により本人確認でき、`/api/v2/projects` から 11 件の参加済みプロジェクトを取得できた。目標プロジェクトは次の通りである。

| プロジェクト | ID | 自動属性又は照合方式 |
| --- | ---: | --- |
| TS2_ITS | 155893 | 「機関名」自動属性、type ID 5 |
| TECH_SUPPORT | 155379 | 「顧客」自動属性、type ID 6 |
| OHR_TOKYO | 161497 | 件名内の顧客値を部分一致 |

認証後のシステム管理画面で次の三つを保存した。

| テンプレート名 | プロジェクト | フィルター項目 | 顧客値の照合元 | 状態 |
| --- | --- | --- | --- | --- |
| TS2_ITS + 機関名 | TS2_ITS | 機関名 | 自動照合 | 有効 |
| TECH_SUPPORT + 顧客 | TECH_SUPPORT | 顧客 | 自動照合 | 有効 |
| OHR_TOKYO + 件名 | OHR_TOKYO | 件名、タイトルに顧客名を含む | 自動照合 | 有効 |

顧客 Code `0220`、名称「一橋大学」を顧客情報画面で表示し、関連タスク及びチケットを確認した。画面上には三つの有効テンプレートが同時に表示され、共通の列で課題を返した。1 ページ目 20 件と 2 ページ目 3 件の合計 23 件で、`TS2_ITS` が 22 件、`TECH_SUPPORT` が 1 件であった。`OHR_TOKYO` は対象プロジェクトとして処理され、今回の顧客値に一致する課題は表示されなかった。同一チケット Key の重複は確認されなかった。

別の顧客 Code `ONEHR`、名称「OneHR株式会社」でも同じ画面を確認した。三つのテンプレートは表示されたが、該当する Backlog 課題は 0 件であった。タイトル照合対象のプロジェクトに該当課題がない場合も画面エラーにはならないことを確認した。

件名列の既定状態は `aria-sort=ascending` で、先頭課題は「【一橋大学】 UHRサーバ」であった。件名見出しを一度クリックすると `aria-sort=descending` となり、先頭課題は「一橋大学_ユーザーの削除、追加について」に変わった。再度クリックすると昇順へ戻った。昇順状態で第 1 ページ末尾から第 2 ページ先頭までの件名順が連続し、23 件の課題 Key はすべて一意であった。

## 5. 実装及び運用上の制限

新しいテンプレートテーブルは適用済みで、現在は三件の有効テンプレートを保存している。Backlog API の課題取得はテンプレートごとに最大 100 件のページを繰り返し取得し、テンプレート単位で 10,000 件を上限とする。複数テンプレートを同時に有効化する場合は、Backlog のレート制限と取得時間を確認する。

共通表示列は `normalizeIssue` が作成する課題 DTO に固定されている。テンプレートごとの個別列は返さず、課題 ID で重複排除した後に件名順で並べ、顧客画面のページングを適用する。初期表示は件名昇順で、件名見出しから降順へ切り替えられる。

## 6. API 権限の整理

今回の API Key は有効で、`TS2_ITS`、`TECH_SUPPORT`、`OHR_TOKYO` を含む 11 件の参加済みプロジェクトを取得できた。Backlog の公式仕様では、`GET /api/v2/projects` の `all=true` は管理者にだけ適用され、指定しない場合は参加済みプロジェクトが対象となる。今回の実測では `/api/v2/projects?all=true` は 403 であったため、プロジェクトを使用できることと、スペース全体の管理者権限があることは同一とは扱わない。

API Key はユーザー単位で発行され、API リクエストの `apiKey` パラメーターで認証する。ユーザー名とパスワードはログイン画面接続の代替経路として保存できるが、プロジェクト一覧と自動属性一覧の取得は現在の実装では API Key を使用する。API Key の値、パスワード及び完全な認証情報は本記録へ保存していない。

公式仕様は [Get Project List](https://developer.nulab.com/docs/backlog/api/2/get-project-list/)、[Authentication and Authorization](https://developer.nulab.com/docs/backlog/auth/)、[Get Custom Field List](https://developer.nulab.com/ja/docs/backlog/api/2/get-custom-field-list/) に記載されている。

## 7. 件名ソートの追加受入

Gateway は課題 ID で重複排除した全結果を件名比較器へ渡し、昇順又は降順を選択してからページングする。顧客情報画面は件名列を受動的なサーバーソート列として表示し、ページ変更ではソート状態を維持し、件名変更時だけ第 1 ページへ戻す。
