# 問合支援の更新日時と回答希望日の時刻表示調査

調査日: 2026-08-17

## 1. 調査対象と要求の分離

### 添付画像および添付文書から読み取れる情報

添付画像は検索結果の表示状態を示す証拠であり、画面上の「更新日時」と「回答希望日」がすべて `00:00:00` と表示されている。画像自体は原因を指示する文書ではない。

プロジェクト規約のうち本調査へ適用する指示は、コード経路を調査し、テスト結果と未確認点を分けて報告すること、コード変更を行った場合はテストを実行することである。今回の明示要求は原因調査であり、修正実装、コミット、リリースは要求されていない。

## 2. 結論

OneOps 側の日時変換関数が、入力に日付だけが含まれる場合に時刻を `00:00:00` として補っていた。検索結果の「回答希望日」はこの経路で日付だけを受け取るため、`2026/08/28` は `2026-08-28T00:00:00+09:00` へ変換され、Portal の `toLocaleString()` が `2026/8/28 0:00:00` と表示していた。今回、日付だけの値を日付文字列として保持し、Portal では日付だけを表示するよう修正する。

「更新日時」も同じ変換関数を使う。実サイト HTML の該当セルが時刻付きなら `2026/08/17 14:35` のように時刻を保持できる。したがって、現在の画像における `00:00:00` は Portal の表示関数が時刻を消している状態ではなく、Gateway が受け取った値に時刻が存在しない場合の既定値が表示された状態である。

## 3. 経路の証拠

1. `app/gateway/inquiry-support-source.mjs:96-105` の `parseDateFromText` は時刻部分を任意として解析し、未指定の場合に `hour = "00"`, `minute = "00"`, `second = "00"` を適用する。
2. 同ファイルの `parseInquirySearchHtml` は一覧セルから `updatedAt`、`createdAt`、`requestedReplyAt` をすべて `parseDateFromText` で生成する。
3. `app/apps/portal-shell/src/InquirySupportPage.tsx:722-730` の `dateTime` は ISO 値を `new Date(value).toLocaleString()` へ渡すだけで、時刻を `00:00` へ丸めていない。
4. `app/gateway/inquiry-support.test.mjs:807-838` は更新日時に `2026/07/27 11:30`、回答希望日に `2026/07/30` を与え、回答希望日の期待値を `2026-07-30T00:00:00+09:00` としている。これは現在の既定動作を固定するテストである。
5. 同テストの詳細フィクスチャ `app/gateway/inquiry-support.test.mjs:848-850` でも更新日時は時刻付き、回答希望日は日付だけである。

## 4. 再現確認

同じ parser へ `2026/08/17 14:35` と `2026/08/28` を入力したところ、前者は `2026-08-17T14:35:00+09:00`、後者は `2026-08-28` になった。修正後の Gateway テスト 43 件はすべて合格した。

## 5. 実サイト原文の追加確認

現在の `ONEHR_UPDS` 設定を使い、認証済み Gateway 経路から UPDS 検索 HTML を読み取った。最初の 5 行の更新日時セルは `2004/01/04`、`2004/02/03` などの日付だけで、回答希望日セルは `2222/12/31` などの日付だけだった。確認対象の原文には時刻が含まれていなかった。

## 6. 未確認点とリスク

今回の検索 HTML では日付だけであることを確認できた。別の検索条件、詳細画面、別の UPDS 契約で時刻が返される場合は、parser が時刻を保持する必要がある。

原文に時刻がない回答希望日は業務上の期限日であり、任意の時刻を推測して付与してはならない。
