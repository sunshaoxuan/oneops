# 問合せ全体分析の応答形式エラー調査

## 1. 目的

問合支援の「問合せ全体分析」で `INQUIRY_ANALYSIS_RESPONSE_INVALID` が発生し、分析結果を表示できない事象の原因を特定し、構造検証の安全性を維持した修正方針を確定する。

## 2. 調査範囲

- 問合せ全体分析の Prompt 生成
- Model API 応答の JSON 構造
- `FULL_TICKET` 応答パーサー
- Portal の失敗表示
- 実行履歴の安全な構造情報

問合せ本文、顧客情報、モデル応答本文、認証情報は証跡へ保存しない。

## 3. 確認結果

実運用で失敗した問合せ全体分析は、5 回分の質問、顧客評価、最終顧客公開回答を含む案件を `FULL_TICKET` として処理していた。Model API は次の必須領域をすべて返していた。

- `roundAssessments` は 5 件で、連番は 1 から 5
- `processFindings` は 5 件で、待ち時間は数値
- 顧客評価との関係は 4 件
- 是正対応は 4 件
- 根拠は 15 件で、各項目に参照キーと理由が存在
- 最終結論は条件どおり設定
- 顧客向け返信案は空文字

不一致は `overallAssessment.risks` だけであり、Model API が 1 件のリスクを文字列として返し、パーサーが文字列配列だけを受理していた。この差によって応答全体が無効と判定された。

## 4. 根本原因

Prompt は `risks` の項目名を指定していたが、1 件の場合も JSON 配列にする条件を明示していなかった。パーサーは意味的に同じ単一文字列を回復できず、構造不正として処理していた。

## 5. 修正方針

1. Prompt で文字列一覧項目を明示し、1 件でも 1 要素の JSON 配列を返すよう指定する。
2. パーサーで単一文字列を 1 要素の文字列配列へ正規化する。
3. オブジェクトと数値は受理しない。
4. 質問回数、連番、対応度、待ち時間、根拠、最終結論条件、空の返信案は厳密な検証を維持する。
5. 既知の形式エラーは画面言語に合わせて案内し、同じ位置から再生成できるようにする。

## 6. セキュリティ確認

調査用出力はキー名、型、件数、連番、列挙値だけに限定した。問合せ本文、モデルの分析文、顧客連絡先、認証情報を標準出力または証跡へ保存していない。

## 7. 結論

原因は Model API の分析能力不足や全文コンテキスト欠落ではなく、単一項目を表す文字列と文字列配列の表現差である。意味的に回復可能な一覧表現だけを正規化し、判断に影響する構造検証を維持する修正で解消できる。
