# 問合支援 要件定義

更新日: 2026-07-30

## 1. 機能名と位置付け

日本語の機能名は「問合支援」、中国語は「问询支援」、英語は「Inquiry Support」とする。第 1 階層ナビゲーション、画面タイトル、ワークベンチの入口で同じ名称を使用する。

本機能は OneOps の保守運用機能である。`inquiries.use` 権限を持つユーザーは、問合せ検索、詳細表示、添付ファイル利用、手動 AI 支援を実行できる。実サイトの接続設定はシステム管理者だけが管理する。

## 2. 実サイトとシステム設定

データソースは `https://ss.onehr.jp/` の UPDS 問合せ検索画面である。システム管理の「外部タスク」には、UPDS サポートサイトの URL、製品、共通ログインユーザー、暗号化パスワード、有効状態を保存する。分析 Model は外部タスク設定から分離し、AI 設定の `INQUIRY` 用途で管理する。業務 API はログイン資格情報を返さない。

システム管理者が設定を読み込む場合、設定 API はパスワードを復号して完全な値を再入力する。パスワード入力は初期状態でマスクし、原文表示とコピーを許可する。保存と接続テストは入力欄の完全な値を送信する。設定 API は `models.settings.read` または `models.settings.write` で保護し、HTTPS と `Cache-Control: no-store` を使用する。監査とログにパスワード原文を記録しない。

分析は登録済みの `GENERAL` Model API を使用する。問合支援は共通 Model 設定と共通呼出 API を利用し、AI 設定自体は変更しない。

## 3. 問合せ検索

検索条件は次のとおりとする。

1. 問合せ No.。省略可能。入力時は No. を完全一致で検索する。
2. キーワード。省略可能。AND または OR を選択できる。追加質問、公開回答、内部コメントを対象へ含めるかを独立して指定できる。
3. 作成期間。開始日は空欄を許可する。終了日はユーザーのブラウザータイムゾーンにおける当日を初期値とし、空欄へ変更できる。両方が空欄の場合は期間を制限しない。
4. 回答希望期間。開始日と終了日は省略可能とし、両方が空欄の場合は期間を制限しない。
5. 更新期間。開始日と終了日は省略可能とし、両方が空欄の場合は期間を制限しない。
6. 顧客。実サイトが返す顧客 ID と表示名から選択する。省略時は全顧客を対象とする。
7. 顧客名。顧客選択と独立した部分一致条件として指定できる。
8. 顧客コード。顧客選択と独立したコード条件として指定できる。
9. 担当者・確認先。実サイトが返す ID と表示名から選択する。省略時は全担当者を対象とする。
10. 担当者未設定。選択した場合は担当者選択を解除し、実サイトの未設定条件を使用する。
11. 担当者・確認先の氏名。担当者選択と独立した氏名条件として指定できる。
12. サブステータス。実サイトが返す選択肢を使用する。
13. カテゴリー。実サイトの階層値を保持し、最上位から子項目へ段階的に選択する。任意の中間階層を検索条件として選択できる。キーワード検索は親から対象までの完全パスを対象とし、選択後も完全パスを表示する。
14. 分類・調査結果。カテゴリーと同じ階層選択を使用し、実サイトの階層値と完全パスを保持する。
15. 質問者名。問題ブロックの質問者名を検索する。
16. ステータス。「すべて」、OPEN、OPEN 子状態、CLOSED、CLOSED 子状態を提供する。ステータス自体は必須である。前記の絞込条件と AI 対応履歴がすべて未指定の場合、「すべて」は使用できない。いずれかの追加条件が指定済みの場合、「すべて」を許可し、実サイトへ空のステータス値を送信する。
17. AI 対応履歴。`inquiry_assist_runs` に補助タスクが存在する問合せだけを表示する。切替操作自体は AI 要求を作成しない。

検索は実サイトを呼び出し、検索完了後の AI 自動呼出と一括 AI 分析を行わない。実サイトの全件数と表示件数を保持し、実サイト側で結果が省略された場合は警告する。

実サイトはキーワードと No. 検索に同じ `k` を使用する。キーワードの結合条件は `kt`、追加質問・回答・コメントの対象指定は `cr`、No. 検索は `sbi` を送信する。両方が指定された場合、No. で対象を特定した後、問合せ詳細へ AND または OR のキーワード一致を適用する。追加記録を対象外にした場合、詳細照合でも初回質問と基本情報だけを対象とする。

日付は作成期間を `cdc`、`cdb`、`cde`、回答希望期間を `rdc`、`rdb`、`rde`、更新期間を `mdc`、`mdb`、`mde` へ対応付ける。顧客、顧客名、顧客コードは `cu`、`cun`、`cuc`、担当者、担当者未設定、担当者氏名は `oc`、`ocno`、`ocn`、サブステータス、カテゴリー、分類・調査結果、質問者名は `ss`、`c`、`it`、`cn` へ対応付ける。選択肢 API は実サイトの値を加工せず保持し、表示名だけを画面へ使用する。

AI 対応履歴検索はローカルの補助タスクから No. を取得し、ステータス、三種類の日付、顧客、担当者、分類などの実サイト条件を問合せごとに適用する。

検索結果の顧客列は実サイトセルの顧客名だけを表示する。質問者は問題ブロックごとに詳細画面で確認する。

検索結果は、問合せ No.、件名、担当者、ステータス、更新日時、回答希望日、顧客の各列で昇順と降順を切り替えられるようにする。初期表示は更新日時の降順とし、更新日時が新しい問合せを先頭へ配置する。並べ替え対象は実サイトから今回返された結果全体とする。実サイトの表示上限により返されていない問合せは並べ替え対象に含めず、既存の省略警告を表示する。

基本条件は検索カード上部へ配置し、顧客、追加日付、分類などは初期状態で閉じた「詳細条件」領域へまとめる。詳細条件を閉じても入力値を保持し、再展開時に復元する。カテゴリーと分類・調査結果は、通常操作では最上位だけを最初に表示し、対象階層の子項目だけを隣の列へ展開する。中幅画面は 2 列、狭幅画面は 1 列の検索レイアウトを使用する。結果テーブルが利用可能幅を超える場合、テーブル内部だけを横スクロールさせる。設定カードと操作バーは `docs/ONEOPS_UI_SPACING_STANDARD.md` に従う。

結果行を選択すると右側の問合せ詳細ドロワーを開く。ドロワーを閉じた後も検索条件、結果、ページ位置を保持する。問合せを開くたびに実サイトの詳細を再取得する。

## 4. 問合せ詳細ドロワー

デスクトップ幅は画面の 88%、最大 1,600 px とする。狭幅画面とモバイルは全画面表示とする。タイトルと基本情報は上部に固定し、詳細本文を独立してスクロールする。

モバイルの幅指定は Ant Design Drawer ルート配下の `ant-drawer-content-wrapper` に適用する。

タイトル領域には、問合せ No.、件名、状態、子状態、担当者、顧客、分類、緊急度、回答希望日、作成日時、更新日時、添付件数、実サイト入口を表示する。顧客連絡先は初期状態で閉じた顧客情報領域へ配置する。

緊急度は基本情報領域の「緊急度」項目だけに表示し、問合せ No. と状態の並びには重複表示しない。件名に「至急」が含まれる場合は値を「至急」として赤色の太字で表示する。それ以外は実サイトの「緊急度」を優先し、空欄または未設定の場合は「一般」とする。

実サイトの独立項目「問合せレベル」は詳細契約に保持する。空欄の場合はタイトル領域へ表示しない。問合せレベルと有効な緊急度は、手動 AI 支援の補足コンテキストに含める。

CLOSED で「サポートサイトへの評価」が存在する場合、満足度、評価コメント、評価受信日時を独立カードで問合せ詳細の最終位置へ表示する。評価コメントがない場合は「コメントなし」と明示する。評価がない問合せには空カードを表示しない。「やや悪い」「悪い」「非常に悪い」などの否定的な評価は、文字ラベルを維持したまま浅い赤色の背景と赤色の評価タグで重大性を示す。

期限超過、未割当、顧客待ち、内部調査中などは制御済みラベルで示す。意味を色だけに依存させない。

## 5. 顧客質問の区分

初回質問を最初の問題ブロックとし、顧客の追加質問ごとに新しい問題ブロックを作る。時間昇順に並べ、最新ブロックを初期展開する。

「追加質問へのコメント」のように質問タイトルを参照するサポートコメントは新しい問題ブロックを作らない。発言は対応する問題ブロックのサポート記録へ配置し、顧客質問本文と会話記録へ重複表示しない。

各ブロックには質問本文、質問日時、回答希望日、関連添付、次の追加質問までのサポート記録、次の返信位置、初期状態で閉じた AI 支援領域を含める。

`questionKey` は問合せ No.、記録種別、日時、内容ハッシュから安定して生成する。

## 6. 会話形式のサポート記録

サポート記録を次の種別へ標準化する。

1. `INTERNAL_DISCUSSION`: 内部コメント、調査、確認記録
2. `CUSTOMER_VISIBLE_REPLY`: 顧客へ公開済みの正式回答
3. `SYSTEM_EVENT`: 担当者、状態、管理項目の変更
4. `ATTACHMENT_EVENT`: 会話または回答に関連する添付

顧客の初回質問と追加質問は問題ブロックの起点として表示する。他の担当者の発言は左側、実サイトの現在ログインユーザーの発言は右側へ表示する。各発言には作者、日時、役割、本文、添付を表示する。公開回答には「お客様に公開」、内部コメントには「内部」の文字とアクセシブルなアイコンを付ける。システム変更は中央のタイムラインとする。

質問、追加質問、内部コメント、公開回答、評価コメントの改行と空行を保持する。HTML の `<br>`、段落、リスト、表行の境界を改行へ変換し、構造を失う単純な `textContent` 圧縮を使用しない。Portal は `white-space: pre-wrap` で表示する。

## 6.1 添付ファイルの表示

添付ファイルの本文抽出、OCR、解析状態、解析結果キャッシュは行わない。問合せ詳細には実サイトの添付 ID、ファイル名、形式、サイズだけを保持する。

画像、PDF、Word、Excel は問合せ詳細より上位に重なるプレビュードロワーで表示する。画像はブラウザーの画像表示、PDF は内蔵 PDF ビューアー、Word と Excel は Office 表示機能を利用する。ドロワーには常にダウンロード操作を配置する。

プレビュー対象拡張子は次のとおりとする。

1. 画像: `png`、`jpg`、`jpeg`、`gif`、`webp`、`bmp`
2. PDF: `pdf`
3. Word: `doc`、`docx`、`docm`
4. Excel: `xls`、`xlsx`、`xlsm`、`xlsb`

その他の形式はプレビューを開かず、一覧から直接ダウンロードする。HTML、SVG、スクリプト、アーカイブなどを OneOps 同一オリジンでインライン表示しない。

ファイル本体は OneOps Gateway を経由してストリーミングし、実サイトの認証情報と署名付き保存先 URL をブラウザーへ公開しない。許可済み S3 オリジンへのリダイレクト時は実サイト Cookie を送信しない。`Range`、`Content-Range`、`Accept-Ranges` を中継する。レスポンスは `private, no-store` と `nosniff` を使用し、許可済みプレビューだけを `inline`、その他を `attachment` とする。`Content-Disposition` の `filename` には ASCII の代替名を設定し、完全な多言語ファイル名は UTF-8 パーセント符号化した `filename*` に設定する。

## 7. 手動 AI 支援

各顧客質問と各サポート発言に低干渉の電球操作を配置する。顧客質問の操作文言は「お客様の質問を分析する」、サポート発言の操作文言は「この返信の品質を分析する」とし、画面表示とアクセシブル名称を一致させる。顧客質問と発言から起動した AI パネルは、その対象の直後へ表示する。

問題ブロック一覧の下、顧客評価の前に、問題ブロックへ属さない「問合せ全体分析」領域を配置する。領域の操作は `anchor=TICKET`、`analysis.mode=FULL_TICKET` として、全顧客質問、全追加質問、全対応記録、添付内容、顧客評価を一つの案件として分析する。分析は現在の対応段階を先に判定し、質問と公開回答の対応、調査進捗、未確認事項、再質問、待ち時間、適用可能な顧客評価、適用可能なサービス品質、リスク、次の対応を段階に合わせて表示する。内部記録は判断根拠として使用し、顧客へ届けた実回答には数えない。実行用の `questionKey` は保存先を確定するためだけに使用し、主分析対象として扱わない。問合せ全体の操作、パネル、履歴を問題ブロックの折り畳み内へ配置しない。

AI パネルはユーザー操作だけで開き、同じ詳細ドロワー内で 1 つだけ展開する。問合せ全体、質問、発言を別の表示位置として保持し、閉じた後に同じ位置から再度開いた場合は、その位置の実行結果と編集済み返信案を詳細ドロワーのセッション内で復元する。検索、詳細表示、問題ブロック切替では AI 要求を作成しない。

AI 支援は現在の問題ブロックに `INTERNAL_DISCUSSION` または `CUSTOMER_VISIBLE_REPLY` が存在するかによって、次の 2 モードへ自動分類する。システムイベントと添付イベントは返信として数えない。

1. `UNANSWERED`: 新規質問または追加質問にサポート返信がまだない。顧客質問の要点と具体的な調査方向を、それぞれ最大 3 件の簡潔な項目で表示する。提示された証拠だけで信頼できる結論を得られない場合は `NEEDS_INVESTIGATION` とし、返信案を空にする。証拠から結論を得られる場合だけ `READY_TO_DRAFT` とし、顧客向け返信案を作成する。
2. `REPLIED`: 内部返信または顧客公開返信が 1 件以上ある。顧客質問の要点、調査方向、現在の回答が顧客質問を満たしているかという評価、実際に回答できていない要点を表示する。現在の回答が十分な場合は `NO_FURTHER_REPLY_NEEDED` とし、回答できていない要点と返信案を空にする。具体的な不足がある場合だけ不足内容を表示し、証拠から安全な補足回答を作成できる場合は `READY_TO_DRAFT`、調査が必要な場合は `NEEDS_INVESTIGATION` とする。

顧客質問から起動した場合は `anchor=QUESTION` を Model API の Prompt へ渡し、選択した顧客質問の要点、曖昧点、不足事実、具体的な調査方向を優先して分析する。問合せ全体の質問、追加質問、対応記録、顧客評価を補助証拠として扱い、主分析を選択した顧客質問から逸らさない。

発言右上の操作から起動した場合は `anchor=MESSAGE` と `focusMessageKey` を Model API の Prompt へ渡す。選択した問題ブロックを分析対象として維持し、問合せ全体の文脈と顧客評価を参照したうえで、選択した回答の顧客質問との関連性、回答範囲、証拠による裏付け、具体的な欠落、リスク、顧客向け表現の品質を `focusedReplyAssessment` へ最大 2 件で明示する。回答が十分な場合はその旨を明示し、不足や追加返信を作為的に生成しない。顧客評価が未回答、回答回避、同一質問の反復、遅延などの具体的な不満を示す場合は、その証拠との整合性を説明せずに回答十分と結論しない。

問合せ全体の AI 補助領域から起動した場合は `anchor=TICKET` と `analysisMode=FULL_TICKET` を Model API の Prompt へ渡し、全問題ブロック、全対応記録、添付情報、顧客評価を一つの案件として評価する。各問題ブロックには質問日時から最初の内部対応までの時間、質問日時から最初の顧客公開回答までの時間、顧客公開回答件数をシステム計算値として含める。最後の問題ブロックに顧客公開回答が存在する場合だけ最終結論を必須とし、存在しない場合は最終結論を `null` とする。整票分析では顧客向け返信案を生成しない。既存の `NEXT_REPLY` 履歴は元の問題ブロック末尾へ読み取り専用で復元する。新しい `NEXT_REPLY` 実行入口は表示しない。

問合せ全体分析の対応段階はサーバー側で次の 4 種類に確定し、Model API に変更させない。

1. `PRE_RESPONSE`: 全問題ブロックに顧客公開回答がない。未回答を品質不良や見落としと断定せず、質問要点、添付内容、調査状況、未確認事項、リスク、次の対応を表示する。サービス品質と最終結論は `null`、顧客評価との関係は空配列とする。
2. `IN_PROGRESS`: 以前の問題には顧客公開回答があり、最新問題に顧客公開回答がない。完了済みの問題だけを回答評価の対象とし、最新問題は対応中として扱う。全体サービス品質と最終結論は `null` とする。
3. `RESPONSE_REVIEW`: 最新問題まで顧客公開回答があり、問合せは未完了である。公開回答の充足度とサービス品質を評価できる。顧客評価が存在しない場合は顧客評価領域を表示しない。
4. `CLOSED_REVIEW`: 最新問題まで顧客公開回答があり、問合せが完了している。公開回答、処理記録、存在する顧客評価を用いて最終評価する。

`FULL_TICKET` 応答の文字列一覧項目について、Model API が意味的に同等な単一文字列を返した場合は、1 要素の文字列配列へ正規化して表示する。対象は各回の見落とし、再質問、顧客評価との関係、全体リスク、是正対応とする。オブジェクトや数値は正規化しない。質問回数、連番、対応度の列挙値、待ち時間、根拠構造、最終結論の条件、空の返信案は厳密に検証する。既知の AI 応答形式エラーは、画面の使用言語に合わせた再生成案内として表示する。

問題分析にはモード、返信案可否、問題要点、調査方向を表示する。`REPLIED` では現在の回答の充足度、重点回答の充足度、回答できていない要点を追加する。根拠は初期状態で閉じる。返信案は顧客向けの丁寧で明確な日本語とし、内部略語を避ける。作成済みの返信案は編集、再生成、コピー、折り畳みを可能にし、詳細ドロワーのセッション内で保持する。実サイトへの送信は行わない。

AI 応答のエスケープ済み改行は編集欄へ入れる前に実改行へ変換する。表示とコピーへ `\n` や `\r\n` の文字列を残さない。

分析対象は問合せ全体、現在の顧客質問、または選択したサポート発言とする。参照範囲には問合せ基本情報、全顧客質問、全追加質問、全内部記録、全顧客公開回答、各記録の可視性、添付解析結果、最終顧客評価を含める。分析対象を切り替えても参照範囲を対象ブロックへ縮小しない。`FULL_TICKET` では全問題ブロックを主分析対象とし、各回の対応度を必ず 1 件ずつ返す。

Model API を使用する AI 補助は、PPTX、DOCX、XLSX の Open XML テキストと内包画像、及び PNG、JPEG、WebP、GIF の画像添付を解析する。抽出テキストは連絡先と秘密情報をマスクして Prompt へ含める。画像は利用者が AI 補助を手動実行した場合だけ、選択中の Model API へ高精度の視覚入力として送信する。添付内容は信頼できない証拠として扱う。1 ファイル 20 MiB、全添付 40 MiB、1 画像 4 MiB、画像合計 12 MiB、最大 10 画像を上限とする。解析件数、画像件数、未対応、失敗、上限超過を実行結果へ保存し、画面に解析範囲を表示する。解析できない添付をファイル名だけで解析済みとして扱わない。

問合せ AI 補助は AI 設定の `INQUIRY` Model API を使用する。CAG を利用する AI助手は独立機能として扱い、問合せ AI 補助の Provider にはしない。

電話、メール、アカウント、パスワード、Cookie、CSRF Token は Model API へ送信しない。問合せ本文を信頼できない証拠として扱い、本文内の操作指示でシステム指示を変更させない。呼出ごとに実際の Model を表示する。失敗時は理由を表示する。

Model API の問題分析、根拠、返信案には `targetQuestionKey`、`focusedMessageKey`、`questionThreads`、`customerEvaluation`、`questionKey`、`messageKey` などの内部項目名と内部 ID を出力させない。分析対象は質問順、質問種別、選択した返信などの業務表現で示す。

根拠から対応する質問または発言へ移動して強調表示できる。

### 7.1 AI 補助履歴

検索条件の「AI 対応履歴」は処理済み問合せを絞り込む用途とする。問合せ詳細では、質問と発言の履歴を元の実行位置へ配置し、問合せ全体の履歴を問題ブロック一覧の下にある独立領域へ配置する。既存の次の返信履歴は元の問題ブロック末尾へ配置する。ドロワー上部に問合せ全体の履歴領域は置かない。

詳細ドロワーを開いた時に `GET /tickets/{ticketNo}/assist-runs` を呼び出し、保存済み履歴を作成日時の新しい順で読み込む。取得した履歴は初期状態で閉じたインライン領域として元の実行位置へ復元する。履歴の読み込み、展開、再展開では AI 補助タスクを作成しない。

補助実行には `anchor` として `TICKET`、`QUESTION`、`MESSAGE`、`NEXT_REPLY` のいずれかを保存する。`MESSAGE` は `focusMessageKey` を必須とし、その他の位置では `focusMessageKey` を持たない。`TICKET` は問題ブロックに依存しない問合せ全体の位置へ復元する。既存データは重点発言がある場合に `MESSAGE`、重点発言がない場合に従来の実行位置である `NEXT_REPLY` へ移行する。過去の解析修正で質問キーが変化した既存データは、問合せに質問ブロックが 1 件だけ存在する場合に限り、その質問の `NEXT_REPLY` へ復元する。複数の質問があり位置を一意に解決できない履歴は、位置不明を明示したドロワー末尾の履歴領域へ表示する。

履歴一覧は実行状態、作成日時、質問ブロック、重点発言、実際の Model、入力 Token、出力 Token、合計 Token を表示する。各履歴は初期状態で閉じ、展開後に問題分析、根拠、返信案、完了日時、失敗理由を読み取り専用で表示する。返信案は実改行を保持し、コピーできる。履歴から再生成と実サイトへの送信は行わない。

問題分析、根拠、保存済み返信案の読み取り専用表示は AI助手と同じ安全な Markdown 表示を使用する。表、見出し、リスト、引用、コード、リンクを解釈し、表は表示領域の横幅に収めてセル内を自動改行する。生 HTML と外部画像を実行または自動取得しない。編集中の返信案は TextArea に Markdown 原文を保持し、コピー時も編集内容の原文を使用する。

待機中または実行中の履歴が存在する間は履歴一覧だけを定期更新する。完了または失敗した時点で更新を終了する。履歴読み込み操作は `INQUIRY_AI_RUN_HISTORY_READ` として操作監査へ記録する。

### 7.2 Model API の固定利用

問合せ支援の AI 補助は `INQUIRY` 用途の「問合せデフォルトモデル」に設定された Model API だけを使用する。問合せ画面と外部タスク設定画面に Provider 選択、Agent Gateway 選択、CAG 会話入口を置かない。Model API の接続、認証、選択 Model ID を確認できる場合だけ AI 補助を実行可能とする。

CAG を利用する全体 AI助手は問合せ支援から独立した共通機能とし、`AI_ASSISTANT_REQUIREMENTS.md` に従う。全体 AI助手の会話や履歴を問合せ AI 補助履歴へ混在させない。

### 7.3 全体 AI助手への参照情報

問合せ詳細で展開中の質問ブロックがある場合、全体 AI助手はチケット No.、質問順、件名を参照中の情報として表示する。質問ブロックを切り替えた時は参照対象を同時に切り替え、詳細ドロワーを閉じた時は解除する。

全体 AI助手から発言した場合は、展開中の `questionKey` を今回の分析対象として明示する。参照範囲には問合せの基本情報、問合せ全体の初回質問、全追加質問、全内部記録、全顧客公開回答、各記録の可視性、全添付ファイル名、最終顧客評価を含める。基本情報にはステータス、サブステータス、担当者名、顧客組織名、分類、緊急度、問合せレベル、作成日時、更新日時、回答希望日を含め、顧客担当者名と連絡先は含めない。分析対象が一つの質問または回答であっても、CAG は問合せ全体と顧客評価を根拠として判断する。質問ブロックの切替は分析対象だけを変更し、参照範囲を対象ブロックへ縮小しない。問合せ AI 補助の実行履歴と全体 AI助手の CAG Conversation は引き続き別管理とする。顧客連絡先と機密情報の除外、表示用 Prompt の復元は `AI_ASSISTANT_REQUIREMENTS.md` に従う。

現在の CAG Conversation で発言時に使用した質問は、詳細ドロワーを閉じた後も灰色の参照済み情報としてチャットへ残す。発言へ使用していない質問は閉じた時に除去する。別の質問を開いた場合は、参照済み情報の下へ活動中の質問を追加する。参照履歴は CAG Task から Session 単位で復元する。

全体 AI助手の活動中または参照済み問合せから開く操作を選択した場合、問合支援は検索を実行せず対象チケット No. の詳細を取得し、参照の `questionKey` に対応する問題ブロックを展開する。対象質問が実サイト更新により見つからない場合は、取得した問合せの最新問題ブロックを展開する。

検索、詳細表示、添付取得、AI 補助タスク作成、開始、完了、失敗をシステム操作監査へ記録する。添付取得は添付 ID と表示方式を記録する。監査には OneOps ユーザー物理 ID、セッション、機能、操作、結果、問合せ参照、Model、要求番号、所要時間を含める。Model API が Token 使用量を返す場合は入力、出力、合計を保存し、未提供の場合はその状態を記録する。

## 8. API とデータ契約

公開 API は次のとおりとする。

1. `GET /api/work-center/v1/inquiry-support/options`
2. `POST /api/work-center/v1/inquiry-support/search`
3. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}`
4. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}/attachments/{attachmentId}`
5. `POST /api/work-center/v1/inquiry-support/tickets/{ticketNo}/threads/{questionKey}/assist-runs`
6. `GET /api/work-center/v1/inquiry-support/assist-runs/{id}`
7. `GET /api/work-center/v1/inquiry-support/assist-runs/{id}/events`
8. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}/assist-runs`

補助要求は必須の `anchor` と任意の `focusMessageKey` を受け取る。`anchor` は `TICKET`、`QUESTION`、`MESSAGE`、`NEXT_REPLY` を受け付ける。`MESSAGE` だけが `focusMessageKey` を必須とする。`TICKET` はサーバー側で `analysisMode=FULL_TICKET` へ固定する。旧クライアント互換として `anchor` がない場合は `focusMessageKey` があれば `MESSAGE`、なければ `NEXT_REPLY` として受け付ける。

共通契約は `InquiryTicketDetail`、`InquiryQuestionThread`、`InquiryMessage`、`InquiryAttachment`、`InquiryEvaluation` とする。`InquiryAttachment` は安定 ID、ファイル名、形式、サイズだけを持つ。`inquiryLevel` は独立して保持し、空欄は `null` とする。`evaluation` は未受信時に `null`、受信時に `satisfaction`、`comment`、`submittedAt` を持つ。問合せ、設定、補助タスク、イベントは安定した物理 ID または業務キーを持ち、Model 設定は物理 ID で参照する。

`InquirySearchInput` は問合せ No.、キーワード、AND・OR、追加記録対象、三種類の日付範囲、顧客、顧客名、顧客コード、担当者、担当者未設定、担当者氏名、ステータス、サブステータス、カテゴリー、分類・調査結果、質問者名、AI 対応履歴を受け取る。`InquirySupportOptions` は担当者、顧客、サブステータス、カテゴリー、分類・調査結果を実サイトの値と表示名の組として返す。

## 9. 受入条件

1. 初回質問、追加質問、内部コメント、公開回答、システムイベントの分類と順序を脱敏済みフィクスチャで検証する。
2. 現在ログインユーザーの発言を右側、その他を左側に表示する。
3. 公開と内部のラベルが文字、アイコン、アクセシブル名を持つ。
4. ドロワー幅、固定ヘッダー、独立スクロール、問題ブロック、モバイル全画面を検証する。
   ドロワーを閉じる時は表示中のチケット No. と詳細データを閉じるアニメーション完了まで保持し、正常な終了を読込失敗として表示しない。
   問合せ詳細と添付プレビューの表示中も、前面の全体 AI助手へ入力フォーカスを移動できるようにする。
5. 検索と詳細表示で AI 要求が作られず、AI 入口を選択した時だけ補助タスクが作られる。
6. 1 パネル制約、質問直後、発言直後、次の返信直後の表示位置、位置別の実行結果、草案編集、コピー、再生成、セッション内復元を検証する。保存済み履歴も同じ実行位置へ復元し、位置を解決できない履歴だけをドロワー末尾へ表示する。
7. 実サイトへ回答を送信する API が存在しない。
8. 根拠から対応発言へ移動できる。
9. 単体テスト、`pnpm check`、本番ビルド、公開、`nginx -t`、Gateway ヘルス、ブラウザーコンソール、スクリーンショットを検証する。
10. 内容検索が `k` と `cr`、No. 検索が `k` と `sbi` を送信し、併用時に両条件を満たす。
11. 管理者設定のパスワードが完全に再入力され、初期状態でマスクされ、原文表示とコピーができる。
12. 「問合せレベル」と「緊急度」を別々に解析し、件名の「至急」と未設定時の「一般」を正しく表示する。
13. AI 対応履歴切替が検索条件だけを変更し、補助タスク数を増やさない。
14. 検索結果の全表示列で昇順と降順を切り替えられ、初期表示が更新日時の新しい順になる。
14. `<br>`、連続 `<br>`、段落境界の改行と空行を保持する。
15. CLOSED 評価の満足度、コメント、日時を問合せ詳細の最終位置へ表示し、否定的評価を浅い赤色背景と文字ラベルで示し、未評価時はカードを表示しない。
16. 画像、PDF、Word、Excel が上位プレビュードロワー、ファイル名、ダウンロード操作、詳細状態維持を満たす。
17. TXT、ZIP、HTML、SVG がプレビューを開かず直接ダウンロードされる。
18. PDF Range 要求、S3 許可オリジン、Cookie 分離、`inline` と `attachment`、`nosniff` を検証する。
19. AI 補助履歴が詳細画面で初期状態では閉じ、詳細表示時に保存済み履歴を読み込んでも AI 補助タスクを作成しない。
20. 履歴の表示で AI 補助タスクが作成されず、Model、状態、質問ブロック、分析、返信案、Token 使用量、失敗理由を確認できる。
21. 履歴返信案の改行を保持し、コピー操作が実サイトへの送信を行わない。
22. サポート返信のない問題ブロックを `UNANSWERED`、内部または公開返信のある問題ブロックを `REPLIED` と判定する。
23. `UNANSWERED` で証拠不足の場合は問題要点と調査方向を表示し、返信案を生成しない。
24. `REPLIED` では現在の回答が顧客質問を満たすかを明示し、実際に回答できていない要点だけを表示する。
25. 現在の回答が十分な場合は `NO_FURTHER_REPLY_NEEDED` とし、追加の不足や返信案を生成しない。
26. 重点返信を指定した場合、問合せ全体と最終顧客評価を入力に残し、選択した回答の一致度、充足度、実際の欠落を個別に評価する。
27. 問合せ AI 補助が Model API だけを使用し、Provider と Agent Gateway の選択操作を表示しない。
28. 全体 AI助手の CAG 会話と履歴が問合せ AI 補助履歴へ混在しない。
29. 展開中の質問ブロックが全体 AI助手へ表示され、質問切替と詳細終了で参照対象が更新される。
30. 全体 AI助手の発言時に現在の `questionKey` が分析対象として示され、問合せの基本情報、問合せ全体の全質問、全対応記録、全添付ファイル名、最終顧客評価が同じ CAG Task の参照情報へ含まれる。30 件を超える対応記録も欠落せず、顧客連絡先は送信されない。
31. 発言済みの質問だけが詳細終了後に灰色で残り、未送信の質問は残らない。
32. 同じ CAG Conversation で別の質問を開くと、既存参照の下に活動中の質問が追加される。
33. 問合せ AI 補助の Model API Prompt に、分析対象の質問または返信、問合せ全体の全質問、全対応記録、全添付ファイル名、最終顧客評価が含まれる。顧客評価と回答充足度が矛盾する場合は、その評価を考慮した判定理由を返す。
33. 実サイトの選択肢から顧客、担当者、サブステータス、カテゴリー、分類・調査結果を読み込み、カテゴリーと分類・調査結果を最上位から段階的に選択でき、完全パスを検索できる。
34. キーワード AND・OR、追加記録対象、三種類の日付、顧客、顧客コード、担当者未設定、担当者氏名、サブステータス、カテゴリー、分類・調査結果、質問者名が実サイトの対応パラメーターへ変換される。
35. 詳細条件が初期状態で閉じ、展開と再収縮ができ、閉じた後も入力値を保持する。検索カードはデスクトップ、中幅、モバイルで画面幅を超えず、検索条件、AI 履歴、検索操作の視覚的な優先順位を維持する。
36. AI 補助の問題分析、根拠、保存済み返信案に含まれる Markdown の表、見出し、リスト、引用、コード、リンクを読み取り専用領域で表示し、生 HTML と外部画像を実行または自動取得しない。
37. 問合せ AI 補助と全体 AI助手の応答に内部項目名と内部 ID を表示せず、分析対象を質問順と質問種別の業務表現で示す。
38. 全体 AI助手の問合せ参照から該当チケットの詳細ドロワーを直接開き、対応する問題ブロックを展開できる。検索 API は呼び出さず、詳細 API だけを呼び出す。
39. 顧客質問とサポート返信の電球が対象位置の分析を起動し、問合せ全体の AI 補助操作、実行パネル、履歴がすべての問題ブロック外かつ顧客評価前の独立領域へ表示される。問合せ全体の Prompt は保存用 `questionKey` で分析範囲を制限せず、全問題ブロックと顧客評価を主証拠として扱う。
40. 問合せ全体分析を実行すると `FULL_TICKET` で処理され、各回の質問と公開回答の対応度、各回の見落とし・再質問・待ち時間、顧客評価との関係、全体品質・リスク・条件付き最終結論、是正対応が独立した 5 領域に表示される。最後の顧客質問に公開回答がない場合は最終結論と返信案を生成しない。
41. `FULL_TICKET` の文字列一覧項目が単一文字列で返った場合は 1 要素の配列として表示できる。構造不正は受理せず、既知の応答形式エラーは使用中の画面言語で再生成を案内する。
42. 顧客公開回答が一件もない問合せ全体分析は `PRE_RESPONSE` となり、サービス品質、最終結論、顧客評価領域を表示せず、現在の対応段階、調査進捗、未確認事項、リスク、次の対応を表示する。
43. 過去の問題に公開回答があり、最新問題に公開回答がない場合は `IN_PROGRESS` となり、最新問題を対応中として扱う。
44. 顧客評価が存在しない場合、Model API は顧客評価との関係を空配列で返し、画面は空の顧客評価領域を表示しない。
45. PPTX にスライド文字列がなく画面画像だけが含まれる場合も、内包画像を抽出して Model API の視覚入力へ渡し、添付解析件数と画像件数を表示する。
46. 添付の重複、上限超過、未対応形式、取得失敗を区別し、未解析の添付がある場合はその制約を画面と分析へ反映する。
