# 問合支援功能需求

更新时间：2026-07-27

## 1. 功能名称与定位

日文功能名称统一使用「問合支援」。中文名称使用“问询支援”，英文名称使用“Inquiry Support”。左侧导航、功能页面标题和工作台快捷入口保持一致。

本功能是 OneOps 的基本运维功能。拥有 `inquiries.use` 节点权限的用户可以查询工单、打开详情、读取附件和人工调用 AI 辅助。真实网站账号设置限系统管理员。

## 2. 真实网站与系统设置

数据来源为 `https://ss.onehr.jp/` 的 UPDS 工单查询画面。系统级设置保存网站地址、产品、登录账号、加密密码、启用状态和分析 Provider 选择。密码不得通过查询接口回传明文。

分析 Provider 支持系统中已登记的 Model 或 Agent Gateway。本功能只消费公共设置和调用接口，不修改 AI 设置与 Agent Gateway 设置本身。

## 3. 工单查询

問合支援页面提供以下条件：

1. 工单 No.。允许留空，填写时进行 No. 精确检索。
2. 内容。允许留空，检索范围包含件名、客户提问、追加提问、正式回答和内部评论。
3. 创建时间范围。开始日期允许留空，结束日期默认使用用户浏览器所在时区的当天日期并允许清空，全部省略表示不限制时间。
4. 负责人。省略表示全部负责人。
5. 工单状态。状态不可省略。
6. AI 处理历史。以 `inquiry_assist_runs` 中已创建过辅助任务的工单号为依据，通过可切换按钮仅显示曾调用过 AI 辅助的工单。切换按钮本身不得创建新的 AI 请求。

查询调用真实网站，不在查询完成后自动调用 AI，也不提供批量 AI 分析。结果保留真实网站的总件数和显示件数。当真实网站截断结果时显示提示。

真实网站使用同一个 `k` 字段承载内容与 No. 查询。内容查询必须提交 `cr`，把追加提问、回答和评论纳入检索；No. 查询必须提交 `sbi`。两个条件同时存在时，先按 No. 精确定位工单，再对完整工单详情执行内容匹配。AI 处理历史查询从本地辅助任务记录取得工单号，并逐票应用状态、日期和负责人等真实网站条件，使结果不受普通列表 500 条显示上限影响。

查询结果的客户列只显示真实网站单元格中的客户名。提问人可能随初始提问和追加提问变化，因此不与客户名合并显示，进入详情后按问题块查看。

查询区域在中等宽度窗口使用双列布局，在窄窗口使用单列布局。查询卡片和结果卡片必须随视口缩小，工单表格超过可用宽度时只在表格内部显示横向滚动，不允许撑宽整个页面。

点击结果行打开右侧工单详情抽屉。关闭抽屉后保留查询条件、结果和页面位置。每次重新打开工单均重新读取真实网站详情。

## 4. 工单详情抽屉

桌面端抽屉宽度为视口的 88%，最大 1600 像素。较窄窗口和移动端使用全屏抽屉。标题和基本信息区固定在顶部，详情内容独立滚动。

标题区显示工单 No.、标题、状态、子状态、负责人、客户、问题分类、紧急度、希望回答日、创建时间、最后更新时间、附件数量和真实网站入口。客户联系方式放入默认收起的客户信息区域。

超期、未分配、等待客户和内部调查中等状态使用受控标签。标签同时使用文字和图标，不能只依赖颜色表达含义。

## 5. 客户问题分区

初始客户提问建立第一个问题块。每次客户追加提问建立新的问题块。问题块按时间正序排列，最新问题块默认展开，较早问题块允许折叠。“追加提问へのコメント”等引用客户问题标题的支持评论区不建立问题块，其中的服务人员发言归入对应问题块的支持记录，不得同时出现在客户问题正文和聊天记录中。

每个问题块包含客户提问正文、提问时间、希望回答日、相关附件、本次提问之后至下一次客户追问之前的支持记录、下一条回复位置，以及默认收起的 AI 辅助区域。

每个问题块拥有稳定的 `questionKey`。该键由工单号、记录类型、时间和内容哈希生成。

## 6. 聊天式支持记录

支持记录标准化为：

1. `INTERNAL_DISCUSSION`，内部评论、调查讨论和检查记录。
2. `CUSTOMER_VISIBLE_REPLY`，已经发布给客户的正式回答。
3. `SYSTEM_EVENT`，负责人、状态和管理项目变化。
4. `ATTACHMENT_EVENT`，与讨论或回复关联的附件。

客户提问和追问作为问题块根节点展示。

其他支持人员的消息显示在左侧，真实网站当前登录人的消息显示在右侧。每条消息显示作者、时间、角色、正文和附件。公开回复显示带可访问图标的“客户可见”标签，内部讨论显示带可访问图标的“内部”标签。系统变化显示为居中的时间线事件。长消息保留完整内容并允许按段落展开。

## 7. 按需 AI 辅助

每个问题块底部的“下一条回复”位置提供低干扰的 `AI辅助` 按钮。每条讨论或回复在悬停和键盘聚焦时提供“以此消息为上下文”动作。

AI 面板仅由用户操作打开。同一抽屉同时只展开一个面板。执行查询、打开抽屉和切换问题块均不得创建 AI 请求。

面板包含问题分析和辅助回复两个视图。问题分析显示事实、争议点、缺失信息、风险、建议确认事项和证据引用。辅助回复提供可编辑草案、重新生成、复制和收起。收起后在当前抽屉会话内保留草案。第一版不向真实网站提交回复。

AI 返回的转义换行必须在草案进入编辑框前转换为真实换行。回复草案内不得把 `\n` 或 `\r\n` 作为可见文本展示，复制内容必须与编辑框中的实际换行保持一致。

默认分析范围为当前客户问题和该问题块内全部支持记录。指定重点消息时，整个问题块仍作为上下文。工单标题、状态、分类和附件解析结果作为补充上下文。

电话、邮件、账号、密码、Cookie 和 CSRF Token 不进入模型。工单正文视为不可信内容，其中的操作指令不能改变系统提示。每次调用显示实际使用的 Model 或 Agent Gateway。Provider 失败时显示原因，不自动切换 Provider。

AI 证据引用可以定位并高亮对应问题或聊天消息。

问询查询、工单详情、附件读取、AI 辅助任务创建、开始、完成和失败必须进入系统操作审计。审计记录包含 OneOps 登录用户物理 ID、会话、功能、操作、结果、工单引用、Provider、实际 Model 或 Gateway、请求编号和耗时。Provider 返回 Token 用量时保存输入、输出和总 Token；未返回时明确记录为未提供。

## 8. 数据接口

公共 API：

1. `GET /api/work-center/v1/inquiry-support/options`
2. `POST /api/work-center/v1/inquiry-support/search`
3. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}`
4. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}/attachments/{attachmentId}`
5. `POST /api/work-center/v1/inquiry-support/tickets/{ticketNo}/threads/{questionKey}/assist-runs`
6. `GET /api/work-center/v1/inquiry-support/assist-runs/{id}`
7. `GET /api/work-center/v1/inquiry-support/assist-runs/{id}/events`
8. `GET /api/work-center/v1/inquiry-support/tickets/{ticketNo}/assist-runs`

辅助请求允许传入可选的 `focusMessageKey`。

详情数据以 `InquiryTicketDetail`、`InquiryQuestionThread` 和 `InquiryMessage` 为公共契约。工单、设置、辅助任务与事件均拥有独立稳定物理 ID 或稳定业务键。Model 与 Agent Gateway 使用其物理 ID 建立数据库外键。

## 9. 验收要求

1. 使用脱敏夹具验证初始提问、追加提问、内部评论、公开回复和系统事件的分组顺序。
2. 验证当前登录人消息在右侧，其他支持人员消息在左侧。
3. 验证“客户可见”和“内部”标签具备文字、图标和无障碍名称。
4. 验证抽屉宽度、固定头部、独立滚动、问题块折叠和移动端全屏。
5. 验证查询和打开详情不会创建 AI 请求，点击 AI 入口后才创建辅助任务。
6. 验证单面板约束、重点消息上下文、草案编辑、复制、重新生成和会话内保留。
7. 验证页面不存在向真实网站提交回复的请求。
8. 验证证据引用可以定位对应消息。
9. 完成单元测试、`pnpm check`、生产构建、发布、`nginx -t`、网关健康检查、浏览器控制台检查和脱敏截图。
10. 验证内容查询提交 `k` 和 `cr`，No. 查询提交 `k` 和 `sbi`，两者同时填写时结果同时满足两个条件。
11. 验证“AI 対応履歴あり”按钮只改变查询条件，返回的每张工单均存在辅助任务记录，并且查询前后辅助任务数量不变。
